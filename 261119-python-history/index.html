    Python 2 → 3: what actually changed

    Python 3.0 was the only release ever designed to break existing code. The goal was to fix mistakes that couldn't be fixed compatibly, above all the confusion between text and bytes. It worked, but moving the ecosystem over took almost twelve years.

    The long migration

        How Python changes: the PEP process

        Almost every change on this page started as a PEP, a Python Enhancement Proposal. A PEP is a design document that explains a change's motivation, specifies it precisely and records the alternatives that were considered. It is debated publicly (today on discuss.python.org) and then accepted or rejected.

        Who decides

        Until July 2018, Guido van Rossum had the final word as Python's “Benevolent Dictator For Life” (BDFL), often delegating individual PEPs to trusted core developers. Since 2019, a five-person Steering Council elected by the core developers has decided (PEP 13). It usually appoints a PEP-Delegate for specialist areas such as typing or packaging.

        “Accepted” means the design is approved. A PEP becomes “Final” only once it ships, which is why this site's look-ahead marks accepted-but-unreleased PEPs separately.

        PEPs about the process itself

        • PEP 1

          PEP purpose and guidelines. Defines what a PEP is, the three types (Standards Track, Informational, Process) and the statuses above. Written in 2000.

        • PEP 8

          Style guide for Python code. Four-space indents, naming conventions and line length. Linters and formatters still enforce it.

        • PEP 20

          The Zen of Python. The design philosophy in 19 lines. Run import this to read it.

        • PEP 13

          Python language governance. How the Steering Council is elected and what it decides, adopted after PEP 8016 won the 2018 governance vote.

        • PEP 387

          Backwards compatibility policy. Normally a feature must be deprecated with warnings for at least two releases before it can be removed. This is why removals in the look-ahead are known years in advance.

        • PEP 602

          Annual release cycle. A new feature release every October since 3.9, each supported for five years.
